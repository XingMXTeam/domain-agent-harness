# 交互复核（interactive-review）

有些检查读代码、读 DOM 都读不出来：键盘事件到底有没有落下去、拖拽是否全程跟手、游戏能不能走到结束状态、路由切换后焦点还在不在。静态探针对这些只能猜，而且两个方向都猜错过——坏的交互被放行，好的交互被判死。这个 skill 是 Harness 三层验证的中间层：由一个带操作能力的全新 Agent 把断言真正做一遍，内核只合并它能验真的结论。

## 工作流

1. **读任务包，不读故事。** `harness packet <feature>` 给你复核任务包：待复核项、每项的 `assert.steps` 与 `assert.expect`、锚点、以及每个目标产物的 SHA-256。不要读 developer 报告、失败日志、state 历史——你是来重新执行断言的，不是来审阅别人对它的叙述的。
2. **按 `tech-design.md` 启动功能。** 起不来 → 所有项的结论就是启动失败；记录下来，停。
3. **逐字执行每个断言。** 在真实会话里（Playwright 或宿主的浏览器工具）用真实输入事件，按顺序做完 steps，不许抄近道，不许用读源码、调 API、跑单测代替交互本身。
4. **观察预期状态。** `assert.expect` 就是合同：成立、部分成立、或不成立。在决定性时刻留证据——截图、会话轨迹、日志——存到该功能的 `review/` 或 `evidence/` 目录。
5. **跑完后重新哈希目标产物。** 内核只合并「绑定的字节仍是磁盘上的字节」的结论。目标在任务包生成后变过，就在备注里说清楚，不要悄悄把结论重新绑到没复核过的新字节上。
6. **把报告写到 packet 给出的报告路径：** 每个已执行项一条，含 `score`（1 / 0.5 / 0）、`note`（做了什么、观察到什么）、`artifacts`（证据，包含每个目标产物）、`artifactSha`（每个目标的哈希）。不要自己跑 `harness review-merge`——校验与合并是编排者的事。

## 人工边界

标了 `verify: "human"` 的项不归你。整条从报告里略去；由人本人以 `"confirmedBy": "human"` 加自己的备注记录。Agent 替人猜判断（提示音好不好听、文案顺不顺口），正是这一层要消灭的自报。

## 没做成，也是一个结果

执行不了的断言——环境挂了、控件够不着、会话崩了——就不要出现在报告里。缺席是诚实的：该项保持未验证、裁决保持 incomplete、阶段重来。绝不能把「没跑成」换算成任何分数。

## 反模式

- ❌ 静态探针或 judge 阅读能判的检查不用这个 skill——文件存在、模式匹配、看截图判版式。交互是最贵的一层，只花在「只能靠做才能知道」的地方。
- ❌ 因为没人盯着就替 `verify: "human"` 项下结论。这一项就等着。无人值守的人工项是 incomplete 裁决，不是邀请函。
- ❌ 看源码下分：「handler 注册了，所以按键有效。」注册不等于落地；只有真正执行过的断言算数。
- ❌ 把昨天的运行绑到今天的字节上——复用产物变更之前的报告、截图或哈希。SHA 绑定就是为拒绝这个而存在的，不要绕它。
- ❌ 执行一个更友好的版本（打字更慢、视口更大、缓存预热）而不是断言写明的那个。断言是合同；放软了，复核什么都证明不了。

## 完成标准

- 每个已执行项在报告里有一条：分数、写明做了什么与观察到什么的备注、真实证据文件、每个目标的当前 SHA-256。
- 每个未执行项不在报告里，并在交接中点名给出原因。
- 报告里没有任何 `verify: "human"` 项。
- 复核期间没有修改被复核的代码。
