# 模式积木与串联判据

> 决策树解决「选哪一级范式（L0–L4）」；本页解决「范式内部，模块之间怎么组合、怎么传数、什么时候能并行」。
>
> 一句话口诀：**纪律没得选，拓扑看耦合 —— 写耦合就单线程、并行只给代码；只读独立才发散，合并只合情报不合动作；值怕变形传键，不怕传值。**

## 一、五块可叠加的模式积木

| 积木 | 解决什么问题 | 关键约束（对应通用契约） | 真实落点 |
|---|---|---|---|
| **1. 路由（Routing）** | 多域或多意图共享统一入口，避免单 Prompt 膨胀 | 规则按顺序匹配；解析失败必须 fail-closed 兜底只读（**C5**） | `scaffolds/plan-execute/src/orchestrator.ts`（Catalog + `brain.md`） |
| **2. 检索（Retrieval）** | 领域知识大、塞不进单次上下文 | 检索只负责「找到原材料」，精确计算前必须先落结构化事实（**C1 / C9**） | `knowledge-mcp.mjs`（L0→L1→L2 目录导航）；`finance` 的 LightRAG `/query` |
| **3. 生成-验证-修复** | 生成结果一次不一定全对，需要自动闭环 | 验收由确定性探针判失败（**C4**）；必设轮次上限与无进展早停（**C7**） | `Atoms` 的 `pipeline.ts`（DOM + `tsc` 探针，最多 3 轮） |
| **4. 只读并行发散** | 大量独立检索/审查任务耗时过长 | 必须同时过「只读、无共享写目标、只合情报」三关，否则回到代码并发 | 30 家公司各自算指标（正例）；32 页搭建由单计划 + 代码分层并发（反例） |
| **5. 人工审批 / 接管** | 不可逆外部写动作、登录/风控/支付、对账升级 | 暂停前落盘 checkpoint，批准后按 `thread_id` 续跑，写动作带幂等键（**C10**） | `finance` 升级外部工程手前；未来 BD 发消息前、浏览器登录/支付接管 |

## 二、串联判据一：传值还是传键

- 交接物**小、结构化、下游是代码** → **直接传值**（如 YAML 流水线里的 `${step.output}` 表达式）。
- 只要沾下面任意一条 → **必须传键 + 强制按源头取数**，缺键直接报错，不许模型编造：
  1. 内容是大文本或二进制资产（长年报、HTML、图片、视频），整包塞不下或稀释注意力；
  2. 是精确数值且要进后续计算（转述必变形：单位、口径、小数位）；
  3. 下游是另一个模型且还会继续转述给下一环。

> 典型正例：`finance` 的 `facts.json`（只传键给纯代码 `compute()`）、`scaffolds/plan-execute` 的 `artifacts/<stepId>.json` 落盘与知识库按需读取。

## 三、串联判据二：多 Agent 发散的准入门槛

多 Agent 并行写同一目标往往因为上下文互不可见导致风格与状态冲突（与 Cognition「默认单线程写，额外 Agent 只贡献智能」的行业共识一致）。允许多个 Agent 发散并行的准入条件**必须三条全过**：

1. 子任务**纯只读**（不写任何共享状态）；
2. 子任务之间**决策互不依赖**；
3. 合并者**只汇总情报**（数据表、审查报告），不合并连贯写成品。

缺任意一条，就回到**单线程规划 + 代码层并发**（例如 `scaffolds/plan-execute` 的 `parallelMap`、分层并发与 `foreach + parallel`）。

## 四、开发时 Agent 与运行时 Agent 的边界

- **开发时（Build-time）**：Antigravity / Claude Code + ShipProof（27 份 Skills + `fh eval`），负责需求澄清、写代码、跑验真。
- **运行时（Runtime）**：部署给用户或业务系统跑的程序本身（L0–L4）。
- 两者共享工程思维（确定性验收优先、禁止自评、状态外置），但绝不把开发时 Skills 误当成产品运行时的「多 Agent 架构」。
