# Agent 架构选型与行业共识

> 这篇文档回答三个问题：编排方式怎么选、行业里做生产的团队实际在怎么做、本仓的设计与这些共识的对应关系。最后给一个按此方法落地的完整示例：finance 财报解析域。

## 一、选型口诀

> **流程常被非程序员调、要审计 → YAML 声明式；有环、长时、要续跑 → 图编排；想完全掌控 → 纯代码薄 harness。三者按确定性分层共存，不是三选一。**

判断的原点只有一个问题：**这一步的动作，在写代码时能定死吗？**

- 能定死、且流程会被业务侧频繁调整 → 把流程写成数据（YAML），改流程不发版
- 能定死、但路径含返工环、执行时间长、崩了要能续跑 → 图编排 + checkpoint，这是运行时能力的差异，不是写法偏好
- 定不死、下一步取决于运行时查到了什么 → 那一格才放模型：模型出结构化计划，代码照计划执行
- 以上都不复杂 → 别上框架。厂商 SDK + 一个 while 循环 + 自己的工具分发，就是生产可用的 Agent

### 三种编排的取舍表

| 维度 | YAML 声明式 | 图编排（LangGraph 式） | 纯代码 / 模型规划 |
|---|---|---|---|
| 流程的载体 | 数据（YAML 文件） | 代码画的图 | 代码（循环）/ 模型运行时生成的计划 |
| 谁能改流程 | 业务方、运营可参与 | 工程师 | 工程师 / 模型 |
| 环与返工 | 弱（靠单步 retries） | 强（条件边 + 环是一等公民） | 循环天然支持，但边界靠自律 |
| 断点续跑 | 靠引擎落盘 state | checkpoint 原生支持 | 自己实现 |
| 审计与 diff | 最好（文本文件） | 中（看代码与图） | 计划即数据时好（可 diff），否则差 |
| 表达力上限 | 低 | 高 | 最高 |
| 典型场景 | 多阶段投放、审批流 | 长任务、带对账返工的管线 | 搭建、修数、开放式操作 |

## 二、行业共识（2025–2026，生产团队的实际做法）

### 1. 12-Factor Agents：Agent 是确定性软件 + 撒点的 LLM 步骤

HumanLayer 的 12-Factor Agents 是目前流传最广的生产实践总结，核心主张：

- 好的 Agent 是「大部分确定性软件，只在对的点上嵌入 LLM 决策」，不是「给个目标加一袋工具循环到底」
- **Own your prompts / context / control flow**：提示词、上下文拼装、控制流都要握在自己手里，不让渡给框架黑盒；框架帮你到 70–80%，最后 20% 必须自己掌控
- 工具调用只是结构化输出：模型产出 JSON，执行与否、如何执行由应用代码决定
- 状态外置、Agent 建模为无状态 reducer：`(state, event) -> new_state`，状态活在外部存储
- 小而专注的 Agent（3–10 步）组合，而不是一个大而全的 Agent

### 2. Cognition：默认单线程，多 Agent 只读

Devin 团队的《Don't Build Multi-Agents》与 2026 年的修正版：

- 把任务拆给多个互不可见上下文的 Agent 并行写，是脆弱之源：上下文不共享、各自的隐含决策互相冲突
- 默认架构是单线程线性 Agent + 上下文工程；上下文工程是「做 Agent 的工程师的第一工作」
- 2026 年的落点：**写操作保持单线程；额外 Agent 只贡献智能（审查、检索），不贡献动作** —— reviewer 模式是被验证可用的多 Agent 形态
- 例外：Anthropic 的多 Agent 研究系统在只读、可并行的检索任务上有效，但代价约为单 Agent 的 15 倍 token；2026 年的对照研究显示等 token 预算下单 Agent 在多跳推理上不输多 Agent。判断标准是任务的耦合度：只读且独立 → 可并行；有写且耦合 → 单线程

### 3. 框架收敛与持久执行

- 框架格局基本收敛：LangGraph、Microsoft Agent Framework（AutoGen + Semantic Kernel 合并）、OpenAI Agents SDK、Claude Agent SDK；MCP 成为默认工具层
- 选型的决定因素从「能不能调工具」变成：状态与持久化、可观测、生态契合
- **持久执行（durable execution / checkpoint）是生产与 demo 的分水岭**：长任务在第 N 步崩溃后从第 N 步续跑，而不是重来
- 厂商 SDK 派崛起：「买循环，自己写业务」—— Claude Agent SDK 把 Claude Code 的 Agent 循环做成库，Pi 的 SDK 化同理

### 4. 护城河是 evals，不是编排

编排框架正在快速商品化。生产团队拉开差距靠的是：评估集、失败样本、对账/验收规则 —— 即「判定对错的资产」。架构会过时，这类资产不会。

## 三、与本仓的对应

| 共识 | 本仓实现 |
|---|---|
| 模型只做决策、代码做执行 | Plan（模型 + JSON Schema）→ Execute（代码并发）→ Review |
| 工具调用只是结构化输出 | plan.json 是纯数据：可校验、可 diff、可人工审 |
| 控制流自己掌控 | 零重型依赖：MCP 客户端、LLM 客户端、Schema 校验全部自实现 |
| 状态外置 | pipeline 的 state.json + artifacts/、session 的 trace.jsonl |
| 单线程写、只读审查 | Review 只读且与执行解耦；验收 pass/fail 由代码判定，模型只解释 |
| 路由往安全侧兜底 | Catalog 路由失败自动落到只读域 qa |
| 契约纪律 | 模型不产出时间值（代码推导）、版本由代码匹配、工具白名单双重约束、缺失项代码补齐不许模型编造 |

**本仓尚缺（往通用方案演进的优先级）**：checkpoint 断点续跑 → human-in-the-loop 中断恢复 → eval 闭环（评估集与回归）→ 可观测产品化。

## 四、示例：按此方法新增 finance 财报解析域

财报解析是一个典型的「固定骨架 + 动态格子 + 外部真值对账」场景，恰好把上面每条共识都用上：

- **为什么不用纯模型规划**：算哪些指标、每个指标的口径（分子分母扣什么）必须逐项写死 —— 口径是契约，不是计划。总则式口径会被模型过度推广（实测：给一句总则，ROAE 修好了、ROA 被带坏；逐项写死后同一个 8B 模型一次全对）
- **为什么要图谱层**：指标要用的数散在年报不同章节，关系（哪个数扣哪个数）不在任何单个文本块里。LightRAG 建图负责「找到」，但图里存的是描述文本，数字是「句子里的数」，不能直接进公式
- **为什么要 facts 层**：图找到的数必须先落成结构化事实（值 + 单位 + 期间 + 出处，过 Schema 校验）钉死，计算只认事实库的键 —— 这是「交接物强制结构化 + 状态外置」的落地
- **为什么对账是代码**：年报自己披露了 ROA/ROAE，是天然的外部真值。校验不经模型的手（弱模型会为自己的错误编可信归因，自查循环救不了）
- **Pi 的位置**：图外工程手。对账反复不过时才被叫来查图谱、补入库，只交结论不算账 —— 对应 Cognition 的「额外 Agent 只贡献智能不贡献动作」

域包蓝图见 `docs/finance-domain/`（设计稿，未接线；接线清单在该目录 README）：brain.md（域内路由）、skills/analyze/spec.md（取数计划的契约与口径清单）、schemas/（plan 与 facts 的 JSON Schema）、executor.ts（存事实 + 计算 + 代码对账）、skills/analyze/review.md（对账规则）。
